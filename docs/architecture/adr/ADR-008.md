# ADR-008: Emit The Request Signals With OpenTelemetry To OpenObserve

- **Status:** Accepted
- **Created:** 2026-11-07
- **Updated:** 2026-11-07
- **Containers:** `backend`
- **Addresses:** [`QR-07`](../../quality-requirements/qr/QR-07.md), [`FR-017`](../../functional-requirements/fr/FR-017.md)

## Context

[`QR-07`](../../quality-requirements/qr/QR-07.md) asks that an operator finds the log point of a failed request within five seconds and reads the P95 of the failures within one minute.
The aggregate needs a histogram, and the per-request point needs an identifier, which a metric label must not carry, because one label value for each request would make the metric grow without bound.
The signals go to OpenObserve, which [`ADR-007`](ADR-007.md) already chose for the analytics, and OpenObserve takes OTLP over HTTP.

## Considered Options

- **OpenTelemetry SDK in the `backend`, exporting a histogram and a log line over OTLP/HTTP.**
  It is the standard that OpenObserve takes, it has a histogram with explicit buckets, and it batches and exports without the request waiting.
- **A Prometheus client that OpenObserve scrapes.**
  OpenObserve would reach the `backend` on a port the team has to open on the VM, and the log would need a second path.
- **The log line only, with the P95 computed in SQL from the durations.**
  It needs no library, but the P95 would be computed from raw lines with no histogram, and the course names the histogram as the aggregate.

## Decision Outcome

Chosen option: the OpenTelemetry SDK in the `backend`.
A layer around every request to an `/api/` path measures the duration with a monotonic clock and, when the request is answered, writes the structured log line and records the histogram `backend_request_duration_ms` with the labels `route` and `outcome`.
The metric is exported every 10 seconds and the log in batches every 1 second, both over OTLP/HTTP to the organization of the environment, and an export that fails is dropped.
[`OBSERVABILITY_ENABLED`](../../deployment.md#the-observability-pipeline) turns it on and it is off by default.

## Consequences

- **Benefit:** the failed request is found by its `request_id` in the log, and its route and outcome are read in the histogram, with no identifier in a label.
- **Benefit:** the product works with collection off, so OpenObserve is an external system and not a container.
- **Cost:** the `backend` depends on two OpenTelemetry packages, and the SDK's log handler is marked deprecated in the version in use, so an update has to be checked.
- **Cost:** a signal that cannot be sent is lost, so a gap in a chart can mean a lost batch and not a quiet period.
