# ADR-004: A User's Own Model Key Stays In The Browser, And The Browser Asks The Model

- **Status:** Accepted
- **Created:** 2026-10-25
- **Updated:** 2026-10-25
- **Containers:** `frontend`, `backend`
- **Addresses:** [`FR-011`](../../functional-requirements/fr/FR-011.md), [`QR-06`](../../quality-requirements/qr/QR-06.md)
- **Decision:** [`DEC-040`](../../decisions.md#dec-040)

## Context

[`ADR-003`](ADR-003.md) has the `backend` ask the language model with a key that the server holds in `.env`.
At the Week 4 meeting the Customer pointed at two limits of that choice: a student may want a model that the `backend` does not support, and a student or a teacher may not want to send their own key to the server.
He asked that no user can see the key of another user ([`DEC-038`](../../decisions.md#dec-038)), and that a user who does not use the key the service provides keeps their own key out of the server ([`DEC-040`](../../decisions.md#dec-040)).
The key that the service provides stays on the server, and the `backend` still stores the cards, because the Customer wants it to remain the source of truth for the data.

## Considered Options

- **The `frontend` asks the language model with the user's own key, and the `backend` keeps asking with the server's key for everyone else.**
  The key of a user is kept in that user's browser and goes only to the language model service, and what the `backend` receives is the answer to store.
- **The user's key is sent to the `backend`, which keeps it for the user.**
  The `backend` would hold the keys of all its users, and a teacher's pages could then be made to show the key of a student, which the Customer excluded when he said that a user's own key "never goes to the server".
- **Only the key of the server, as in [`ADR-003`](ADR-003.md).**
  A student could use no model that the `backend` does not support and could not keep a key private, which the Customer asked for.

## Decision Outcome

Chosen option: the `frontend` asks the language model with the user's own key when the user has set one, and the `backend` keeps asking with the key of the server when the user has not.
The `backend` never receives and never returns a key of a user, and it keeps saving and processing the cards.
The record documents the Customer's [`DEC-040`](../../decisions.md#dec-040).
It is not built yet: today only the `backend` asks the model, as [`ADR-003`](ADR-003.md) says.

## Consequences

- **Security (Confidentiality):** the key of a user does not reach the server or the pages of another user, which keeps [`QR-06`](../../quality-requirements/qr/QR-06.md) reachable.
- **Reliability (Fault Tolerance):** a request that fails in the browser must still leave a card for the word, so the `frontend` has to hand the failure to the `backend`, or [`QR-01`](../../quality-requirements/qr/QR-01.md) is not met for these users.
- **Maintainability (Testability):** the repeating and the reading of the model's answer, which `backend/app/llm.py` does and `python -m pytest` tests, must also run in the browser, where the repository has no tests yet, so [`QR-02`](../../quality-requirements/qr/QR-02.md) does not reach it until they are written.
- **Performance Efficiency (Time Behaviour):** the time to show the cards after the answer arrives is measured in the browser as well for these users, as [`QR-05`](../../quality-requirements/qr/QR-05.md) says.
- **Cost:** the logic that asks the model exists twice, once in each container, and the two must agree.
