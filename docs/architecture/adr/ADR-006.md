# ADR-006: Give Each Learner A Database File Named By A Library Code

- **Status:** Accepted
- **Created:** 2026-11-07
- **Updated:** 2026-11-07
- **Containers:** `frontend`, `backend`, `database`
- **Addresses:** [`FR-015`](../../functional-requirements/fr/FR-015.md)

## Context

The product has one database file for every environment, and it has no accounts, so every person who opens a deployed product sees and can delete the cards, the decks and the texts of everybody else.
A learner also needs to open their own cards again on another device, and after the browser data was cleared.
The team has a few days for this change, the university VM has no way to send an e-mail, and the Customer asked to leave the teacher's side, which needed accounts, out of the product ([`DEC-050`](../../decisions.md#dec-050)).

## Considered Options

- **A database file for each library, chosen by a random code that the browser sends.**
  The code names the file, the learner keeps the code and can enter it in another browser, and no route or query changes, because the choice is made once, where the connection is opened.
- **Accounts with an e-mail address and a password.**
  It gives recovery by e-mail and sign-in from any device, but it needs a table of users, a user on every row with a migration of the cards that exist, passwords and sessions, and a way to send e-mail that the VM does not have.
  It was left for a later story, because it did not fit the days left and it asks for a decision of the Customer.
- **One database file with a library column in every table.**
  It keeps one file, but every query of the backend has to filter by the library, and one forgotten filter shows the cards of one learner to another.

## Decision Outcome

Chosen option: a database file for each library, named by a random version 4 UUID that the browser makes, keeps and sends in the header `X-Library-Code`.
The backend opens the file of the code in the one place that opens a connection, so the routes and the queries are the ones they were, and a library is never mixed with another one.
A request without a code keeps using the default database file, which the API tools and the tests use.

## Consequences

- **Benefit:** a learner has a library no other learner sees, and can open it again from another device or after clearing the browser data by entering its code.
- **Cost:** the code is the only key, so whoever has the code opens the library, and a learner who loses the code loses the library, because the product keeps no e-mail address and has no way to recover it.
- **Cost:** a deployment has many small database files, and a backup of the deployment has to copy the folder `libraries` next to the default database file, as [`deployment.md`](../../deployment.md#deploy-by-hand) says.
- **Cost:** a new version of the tables is applied to a library the first time the product uses it after it starts, not to all of them at the start.
- **Cost:** the default database file of a deployment is no longer the one the web page uses, so the cards that exist before this change stay in it and a learner opens them only by an API tool.
