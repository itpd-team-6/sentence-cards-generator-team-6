# ADR-002: Change The Database With Numbered Migrations Run Once In Order

- **Status:** Accepted
- **Created:** 2026-10-22
- **Updated:** 2026-10-22
- **Containers:** `backend`, `database`
- **Addresses:** [`QR-02`](../../quality-requirements/qr/QR-02.md)

## Context

The `database` is an SQLite file that a learner keeps between versions of the product, and a new version often needs a new table or column.
The learner's existing cards must survive such an update, and the team needs a way to change the schema that a test can run from a clean checkout.
Nobody self-hosting the product runs a database administrator, so the schema change has to happen when the product starts, not by a hand-run script.

## Considered Options

- **Numbered migrations run once each in order, with the last number kept in the database.**
  Each schema change is a numbered step; on start the product runs the steps the file has not run yet, in order, and records the new number, so the same file is never migrated twice.
- **Recreate the schema from one current definition on start.**
  Simple to write, but it cannot carry an existing file forward without dropping and rebuilding its tables, which loses the learner's cards.
- **A third-party migration framework.**
  More than the product needs for one SQLite file, and another dependency a self-hoster must install, against the small-footprint aim of [`CON-07`](../../product-vision.md#con-07).

## Decision Outcome

Chosen option: numbered migrations in `backend/app/database.py`, run once each in order, with the number of the last one kept in the database (`PRAGMA user_version`).
A migration and its new version number are written together in one transaction, so a migration that fails rolls back and leaves the database at the version it had, with its cards.
To change the tables, the team adds a migration to the list rather than editing one already on `main`.

## Consequences

- **Maintainability (Testability):** the migration list is in `backend/app/database.py`, a critical module the backend tests cover, so a broken migration order makes the tests fail, which keeps [`QR-02`](../../quality-requirements/qr/QR-02.md) reachable.
- **Benefit:** a learner's existing cards are carried forward across a schema change, because only the migrations the file has not run are applied and a failed one rolls back.
- **Cost:** a migration already on `main` is never edited, so a mistake in one is fixed by a new migration, not by changing the old one.
