# FR-017: Expose The Quality Signal Of Each Request With Its Environment

- **Status:** Active
- **Traces to:** [`US-14`](https://github.com/itpd-team-6/sentence-cards-generator-team-6/issues/NNN), [`QR-07`](../../quality-requirements/qr/QR-07.md), [`ADR-008`](../../architecture/adr/ADR-008.md)
- **Containers:** `backend`

## Behavior

When the `backend` answers a request to an `/api/` path, the `backend` shall write one structured log line with the fields `request_id`, `method`, `route`, `status`, `outcome` and `duration_ms`, as [the signals](../../observability.md#the-signals) list.

When the `backend` answers a request to an `/api/` path, the `backend` shall record the duration of the request in the histogram `backend_request_duration_ms` with the labels `route` and `outcome`.

The `backend` shall send the same `request_id` that the log line carries to the caller in the `X-Request-ID` response header.

The `backend` shall label a request with the path template that matched and not with the path, and shall carry no text, word, sentence, library code or learner identifier in a signal.

The `backend` shall export the signals of an environment only to the organization of that environment in OpenObserve.

When `OBSERVABILITY_ENABLED` is not true, the `backend` shall send no signal.

The `backend` shall export a signal without making the request of the learner wait for it.

When OpenObserve does not answer, the `backend` shall answer the learner as it does without observability and shall drop the signal.

## Acceptance Criteria

### AC-01

Given a request to an `/api/` path, when the `backend` answers it, then one log line carries its `request_id`, `route`, `outcome` and `duration_ms`, and a request to another path writes none.

Test: `backend/tests/test_observability.py::test_a_request_to_the_api_writes_one_log_line_with_its_labels` and `backend/tests/test_observability.py::test_a_request_that_is_not_for_the_api_writes_no_line`.

### AC-02

Given a request for the cards of a text that does not exist, when the `backend` answers it, then its log line has the route as the path template, the outcome `client_error` and no identifier from the path, and its `X-Request-ID` header equals the `request_id` of the line.

Test: `backend/tests/test_observability.py::test_a_failed_request_of_the_core_task_is_labelled_with_its_failure`.

### AC-03

Given two requests, when the `backend` answers them, then they have different identifiers.

Test: `backend/tests/test_observability.py::test_every_request_has_its_own_identifier`.

### AC-04

Given a status, when the `backend` labels the request, then the outcome is `ok` below 400, `client_error` from 400 to 499 and `server_error` from 500.

Test: `backend/tests/test_observability.py::test_the_outcome_follows_the_status`.

### AC-05

Given OpenObserve, when requests are answered, then the histogram and the log lines reach the organization of the environment over OTLP/HTTP with that environment's user, labelled by route and outcome.

Test: `backend/tests/test_observability.py::test_the_signals_reach_the_backend_over_otlp`.
